# Wooden board and agent controls

The board uses Three.js 0.185 with its WebGL renderer. React owns the game state and the HTML controls; the scene draws that same state. The original Convex room API remains the authority for online games. Local games start without authentication or a network request.

## Renderer choice

Three.js provides the geometry, materials, lighting, ray casting, and camera controls this small scene needs. Its WebGPU renderer can fall back to WebGL 2, but the [current Three.js manual](https://threejs.org/manual/en/webgpurenderer) still describes it as experimental and notes that some scenes perform better with WebGLRenderer. This board does not need compute shaders or a new post-processing pipeline. The simpler WebGL renderer is sufficient.

The mesh and material resources are shared. The renderer runs only after a state change, a camera movement, resizing, or during a 280 ms bead drop. Reduced-motion preferences skip the drop animation. Pixel density is capped at 1.75. Unmounting disposes the controls, observers, animation frames, textures, geometry, lighting resources, and renderer.

Wood grain is generated locally, and beads are lathed from a profile with an actual center hole. No external image, model, font, or HDR download is required. The supplied photograph was a visual reference; it is not distributed with the app.

## AI and keyboard interaction

A canvas alone does not expose a useful game state to a browser agent. The [HTML standard](https://html.spec.whatwg.org/multipage/canvas.html) recommends matching interactive canvas regions with focusable controls. This app uses ordinary HTML buttons over the projected pegs. The map displays those same buttons in a fixed grid.

- Each peg has a stable coordinate, A1 through D4, independent of camera rotation.
- Each accessible name includes its complete stack, bottom to top, and the next legal move. For example: `A1, bottom to top: Maple, Walnut; drop Maple at level 3`.
- `data-column`, `data-stack`, and `data-next-level` expose the same information to DOM tools. `data-stack` always has four entries, including empty levels.
- `aria-disabled` marks full pegs, an opponent's turn, pending network operations, and completed rounds. The click handler also enforces that state. The online backend independently checks every move.
- The table exposes `data-game-status` and `data-current-player`. A live status announces turns and the winner.
- Tab reaches controls. Arrow keys move between peg buttons, Home and End reach the first and last peg, and Enter or Space plays. Unavailable pegs remain focusable so their contents can be read.
- Pointer users can click a peg or bead directly. Dragging rotates the board and does not place a bead. Top view and the map provide alternatives when another stack blocks the view.
- If WebGL initialization fails or the context is lost, the playable map remains available.

[WebMCP](https://developer.chrome.com/blog/webmcp-epp) offers structured browser tools, but its published documentation still presents an early preview. This implementation does not require agents or browsers to support it. A future WebMCP adapter should call the same move handler and read the same state, without adding another game engine or bypassing turn checks.

## Validation

Run `vp run check` and `vp run build`. Game tests cover gravity, turn alternation, all 76 winning lines, horizontal and vertical wins, a space diagonal, draws, invalid or full pegs, moves after a win, immutable positions for undo, and the accessible stack description.

For browser verification, use `vp run dev:frontend --host 127.0.0.1 --port 5176` with the development environment generated by the supported setup. Two distinct origins, `127.0.0.1:5176` and `localhost:5176`, provide separate guest storage for testing both sides of a room. Test the controls through their accessible names, verify the resulting board after each move, and use the map for a fixed view.
